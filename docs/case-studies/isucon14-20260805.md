## 結論(最終ベンチ前)

- score 9511 の一番強い機能上の制約は matcher だった。0.5秒ごとの呼び出しで1 ride
  しか割り当てられず、上限は約2 rides/s。75.6秒の run で matching は145回、最後に
  `長時間マッチングされませんでした` が1件出た。
- CPU、disk、memory、DB pool が先に飽和した証拠はない。ただし当該 snapshot の
  procstats はサービス起動からの約78分を平均しており、run の CPU% としては使えない。
  「CPUが余っていた」と断定せず、正しい75.6秒区間を持つ hoststats と pool wait だけを
  除外根拠に使った。
- 次の総需要は notification polling。app notification 12.7万回、chair notification
  6.7万回が、latest ride、status、auth、coupon、user、chair stats を反復していた。
  不変データの cache と明示 invalidation、status query の1本化、chair stats 集約へ変更した。
- 最終ベンチはまだ実行していない。この文書の「実装済み」は code/build/service smoke の
  意味であり、score 改善や benchmark correctness の確認とは分ける。

## 時系列の判断と実装

### 1. 計測可能な構成へする

計測前に Go app を isutools driver / HTTP middleware へ接続し、DB target、DB pool、
initialize boundary を登録した。nginx→app は UNIX socket、pool は100、MySQL driver は
`interpolateParams=true`。この段階の目的は「速くする」より、次の run を同じ境界で
説明できるようにすること。

実機 commit: `e4bd443 perf: instrument and tune Go serving path`

### 2. 高コスト query の fan-out と scan を減らす

`chairs` / `chair_locations` / `rides` / `ride_statuses` / `coupons` に複合 index を追加。
nearby chairs の chair→rides→status→location N+1 を1 queryへまとめ、owner chairs の
window 対象を owner の chair に限定した。

実機 commit: `e70f002 perf: reduce ride lookup SQL fan-out`

### 3. correctness error に直結する matcher 上限を外す

事実:

- matcher は0.5秒ごとに呼ばれ、旧実装は1回に1 rideだけ割り当てた。
- score 9511 run は145 calls、最後に code 32 (`長時間マッチングされませんでした`) 1件。

推論:

- 実装上限は約2 rides/s。CPUやpoolに余力があっても queue はここで直列化される。

修正:

- 古い未割当 ride と利用可能 chair を最大64件 `FOR UPDATE` で取得。
- 1 transaction 内で一対一に割当。
- batch 化後は interval を0.5秒へ戻した。上限は最大128 assignments/sで、idle 時の
  10Hz polling を残さない。

実機 commit: `dff2ffb perf: batch ride matching`

検証: Go test/build 成功、service active。benchmark correctness は最終 run 待ち。

### 4. notification/auth の短い query を繰り返さない

事実:

- app notification 12.7万回、chair notification 6.7万回。
- 上位10 SQLの多くが notification 1回ごとの auth/latest/status/fare/user/stats。

修正:

- access token→user/owner/chair、ID→user/chair、current ride、確定 fare を process cache。
- immutable な値だけを cache。chair activity、matcher assignment、ride evaluation は
  transaction commit 後に明示更新または invalidation。
- `/api/initialize` のDB再構築直後に全 cacheを clear。
- unsent status と latest status の2 queryを、unsent優先・なければlatestの1 queryへ統合。
- chair stats の ride→statuses N+1 を3つの `EXISTS` + aggregate 1 queryへ変更し、
  evaluation commit後に invalidation。

実機 commit: `055d788 perf: collapse notification polling queries`

検証:

- Go test/build 成功。
- status query `EXPLAIN ANALYZE`: 0.036ms、`ride_statuses_ride_created` 使用。
- chair stats aggregate `EXPLAIN ANALYZE`: 0.052ms、`rides_chair_updated` と
  `ride_statuses_status_ride` 使用。
- benchmark correctness と実際の query count 減少は最終 run 待ち。

### 5. isutools UI を「最初に見る順」にする

score 9511 の画面には全情報があったが、HTTP/SQL/resource/failure が別セクションで、
初見では優先順位を人が再構成する必要があった。レポート先頭へ
`Bottleneck Overview` を追加し、次を同じ表に表示する。

- HTTP / SQL の最大累計 demand
- proxy 5xx / 499 (appへ届かなかった可能性)
- proc interval と run interval の一致確認後の CPU busy/idle
- DB pool wait
- SQL row efficiency
- disk util / IO PSI / major faults

これは自動根本原因判定ではない。疑いと詳細 evidence を結ぶ triage である。

isutools commit: `ec3c0e1 feat: summarize report bottlenecks`

### 6. 運用上の誤判定を直す

- EXPLAIN user に対象schema SELECTだけを与えており、`performance_schema.* SELECT` が
  不足していた。直接GRANT 3行を README preflight に固定した。
- nginx entrypointだけ読む旧版は include先を見落とし、directory指定はsymlinkを
  二重読込した。現在版は include graph + symlink dedupe。旧版向けに `nginx -T` の
  effective snapshot 手順を README に残した。
- matcher unit は `ExecStop=... SIGQUIT` で通常restartをcore-dump扱いにしていた。
  `SIGTERM`へ変更し、curl response bodyをjournalへ流さないようにした。
- API response gzip は benchmark protocolを壊したため無効化。静的assetの圧縮とは
  分けて扱う。

## 失敗と学び(ブログ本文候補)

1. **pass/failをscoreより先に見る。** 9,511は9,291より高いがfailなので勝ちとは言えない。
2. **CPU%の前に区間を見る。** 0.75%という見栄えの良い数字でも、78分平均なら今回の
   benchmarkを説明しない。
3. **短いqueryも回数で最大になる。** 0.5msを十数万回呼べば、indexを増やすより
   handlerのfan-outを消すほうが先になる。
4. **throughput上限はresource飽和なしに作れる。** matcherの1 call 1 assignmentは
   CPU・disk・poolが空いていても2 rides/sを超えない。
5. **計測ツールの欠損も成果物。** EXPLAIN権限、nginx include、ULID path、proc boundaryを
   issueと回帰testへ変えると、次の利用者は同じ穴に落ちない。
6. **実装とbenchmark proofを分ける。** build成功、service 200、EXPLAIN高速は必要条件。
   scoreとcorrectnessは最終benchmark artifactだけが証明する。
