# ISUCON14 実機を isutools で改善した判断ログ (2026-08-05〜06)

この文書は、`../ekusiadadus.com` でブログ記事にするための一次記録である。
計測 artifact、実装 commit、観測事実、推論、失敗とrollbackを分離し、後から
「なぜその順で直したか」を再構成できるようにする。

参考記事:

- [private-isu で50万点を超えるまで with isutools](https://ekusiadadus.com/ja/blog/private-isu-500k-with-isutools)
- 原稿化するときは「スコア推移 → 計測環境 → 判断の時系列 → 失敗 → 次の設計」の順にする

## 結論

- 復旧後の比較可能な clean run `95,656` から、correctnessを維持した採用版は
  **`207,152` (`+116.6%`)** まで伸びた。観測中の最高 clean score は
  **`218,468` (`+128.4%`)** だが、その後に見つかった空車公開競合を構造的に塞ぐ前の値なので、
  最終採用値にはしない。
- 現在のmatcherは0.5秒ごとに最大64件を解く **rolling Hungarian** である。
  すでに割り当てたrideを再最適化せず、将来のchair位置・解放時刻も予測しないため、
  lifelong schedulerではない。
- 実データの軌跡では、540 chairs、115,875 points、3,678 rides、3,307 assignmentsを可視化し、
  **同一rideの再割当ては0件**だった。実装の読み取りと実データが一致した。
- 最終runの最大需要はnotification pollingで、DB poolは100/100、618,999 waits、平均38.6ms待ち。
  一方でhost CPUはbusy 58.7% / idle 41.0%、disk util最大14.5%だった。次に外すべき制約は
  CPUやdiskではなく、polling fan-outとDB接続の公平性・有用仕事の飢餓である。
- DB poolを100から250へ増やすだけの案は、待ち時間を減らしても評価完了数とscoreを落とした。
  接続数の増加は大量pollerをさらに通し、有用なwrite/evaluationを救わなかった。
- dummy wait付きHungarianはdispatch距離p95を561→25へ改善したが、128 rideをDB transaction内で
  解いたためpool待ちとnotification latencyを増やし、scoreは187,425へ低下した。cost設計は採用候補、
  transaction境界は不採用と分けて判断する。

## 時系列の判断

### 1. まず計測境界とSQL fan-outを直す

初期実装へisutoolsのSQL driver、HTTP middleware、DB pool、initialize boundaryを接続し、
nginx→appをUNIX socketにした。`chairs`、`chair_locations`、`rides`、`ride_statuses`、
`coupons`へ複合indexを追加し、nearby/ownerのN+1をまとめた。

次にaccess token、user/chair、current ride、fareなどの不変または明示invalidate可能な値をcacheし、
notificationのunsent/latest statusを1 queryへまとめた。これらが復旧後run 95,656の土台である。

主要commit: `e70f002`, `e4bd443`, `dff2ffb`, `055d788`, `18a7f62`。

### 2. matcherの直列上限をrolling Hungarianへ置き換える

旧matcherは0.5秒に1 rideだけ割り当てるため、資源が余っていても約2 assignments/sが上限だった。
`2f9fc96`では、現在未割当ての古いrideと現在freeなchairを最大64件ずつ取り、
距離/speedと大きなmiss penaltyをcostにしたHungarian法で一括割当てした。

これは各tickで現在集合に対する最小費用matchingを解く。以下は行わない。

- すでにcommitしたassignmentの解除・再割当て
- 次のwindowで到着するrideの予測
- busy chairの完了時刻と完了位置を候補に含めること
- waiting cost、assignment churn、commit horizonを含む時間展開最適化

したがって「普通のHungarianを繰り返すrolling horizon」であり、LORRのようなlifelong最適化ではない。
A*も障害物のないManhattan距離計算には不要で、今の主問題は経路探索よりdispatch schedulingである。

### 3. hot pathから同じ位置・速度・空車判定を外す

`e6bac97`でchair位置とmodel speedをmatcher向けにcacheし、`c6acff4`でnearbyも同じ位置cacheを再利用。
`8e41fc2`ではnearbyのDB workを単純化した。これによりclean scoreは210,955まで伸びた。

同じmicrosecondに複数座標が届くため、`created_at`だけでは順序が決まらなかった。
`3584d1d`で`created_at, id`順へ固定したが、ULID生成順とchairの論理的な移動順は一致しない場合がある。
最終的に`5149369`で隣接sample間距離をchair model speedでcapし、code 26を消した。
このrunが観測最高の218,468だった。

### 4. chair stats cacheの失敗をper-ride snapshotへ直す

`a6d4503`はchair全体のstatsを安全にcacheしようとしてride評価との整合性を壊し、
code 33が201件出てfailした。`2f6701b`で直ちにrollbackした。

`cdd5994`では共有global集計をやめ、ride lifecycle単位のsnapshotへ変更した。
scoreは207,639まで戻ったが、座標順序由来のcode 26が116件見えたため、前節のspeed capへ進んだ。

### 5. DB poolを増やすだけでは有用仕事が増えなかった

最良runではpool 100/100、632,395 waits、平均約41ms待ちだったため、`23a5d71`で250へ増やした。
平均waitは約19msまで下がった一方、scoreは188,267へ低下し、評価完了数も3,295→2,794へ減った。
host idleは増え、app/MySQL CPUは下がった。

解釈は「DBが速くなった」ではなく、notification pollerがより多くのconnection slotを占め、
ride status/evaluationなどの有用仕事を飢餓させた、である。`47fd30f`で100へrollbackした。

### 6. nearbyの空車公開競合を、世代付きin-memory reservationで塞ぐ

benchmark code 30は、DBの`evaluation IS NULL`がchairの6 status確認完了より早くfreeを表すため発生した。

- `8aa68ea`: matcher transaction全体とnearby全体をRW lockで囲み、cleanだが190,159へ低下。
- `adda01d`: 最後だけSQL再確認したが、`evaluation IS NULL`という条件自体がlifecycleを表せず失敗。
- `6c16665`: in-memory busy setを導入したが、notificationがDB connectionを保持してmatcher lockを待ち、
  pool 100本を使い切るlock inversionを作って61,299 / fail。
- `68e0ad6`: `chairID -> rideID`をreservation generationとして保存。COMPLETED後は
  `CompareAndDelete(chairID, rideID)`で自分の世代だけを解放し、DB connectionを保持して
  matcher lockを待つ経路を削除。古いCOMPLETEDが新しいrideのreservationを消さないtestを追加。

最終ベンチは207,152、`pass=true`、`map[]`。218,468より5.2%低いが、競合を偶然踏まなかった
高いrunより、lifecycle correctnessを構造的に保証したこちらを採用した。

### 7. dummy waitは長距離dispatchを消したが、transactionを長くした

軌跡で2都市間の長いdispatchが見え、旧Hungarianがすべてのrideへ実chairを強制していることを確認した。
`1f4cf34`ではrideごとにdummy(wait)列を追加し、新しい遠距離rideは最大5秒待たせ、starvation時だけ
遠距離を許可した。遠距離rideが候補先頭を塞がないようride windowも64→128へ広げた。

品質指標は狙いどおり改善した。

| 指標 | `cdd5994`軌跡 | `1f4cf34`軌跡 |
|---|---:|---:|
| dispatch Manhattan p50 | 20 | 9 |
| dispatch Manhattan p95 | 561 | 25 |
| dispatch Manhattan max | 724 | 54 |
| pickup到着時間への不満 | 13.7%（直前採用run） | 0.0% |
| matching待ちへの不満 | 94.1%（直前採用run） | 87.7% |

一方、scoreは207,152→187,425 (`-9.5%`)。matcher avgは92→116ms、p95は268→537ms、
DB pool平均waitは38.6→48.9ms、app/chair notification p95は134→268msへ悪化した。
原因はdummy costではなく、128×(64+128)のHungarianをride/chair rowをlockしたtransaction内で
計算したこと。次案ではread-only snapshotとcost計算をtransaction外へ出し、commit時だけ候補を
再検証・conditional updateする。1回のベンチへ混ぜず、`1f4cf34`は不採用実験として保存する。

### 8. 公式解説どおりnotificationをキャッシュし、matcher windowを縮めた

`1f4cf34`の次に、レポート最大の累計時間だったapp/chair notificationを改善した。ISUCON14公式解説の
「JSON APIの状態でもライドを丁寧にキャッシュできる」「全endpointが30ms以内なら理想」という記述と、
実測のnotification status select約60万回が一致したため、SSE移行ではなく状態遷移で無効化する
in-process response cacheを選んだ。

実験は失敗も含めて次の順に行った。

|---|---|---:|---|
| `ff9bf40` | [`20260806-105659.934929660-000001`](http://localhost:19191/20260806-105659.934929660-000001) | 196,947 / fail `32` | status未変更時を100msへしたが、active rideの次状態検知も遅延 |
| `4989df5` | [`20260806-110754.047197302-000001`](http://localhost:19191/20260806-110754.047197302-000001) | 191,253 / pass | 100ms backoffをrideなしだけへ限定。安全な中間点 |
| `b4f958d` | [`20260806-112525.526742133-000001`](http://localhost:19191/20260806-112525.526742133-000001) | 150,218 / fail `30,32` | response cacheでDB待ちは激減したが、複数の未送信statusを1件目で塞いだ |
| `64685b2` | [`20260806-113535.652281368-000001`](http://localhost:19191/20260806-113535.652281368-000001) | 218,254 / fail `32` | 公式例の距離400と300ms starvation fallbackへ変更したがstatus詰まりが残存 |

cacheはrideごとのgenerationを持ち、status挿入、chair assignment、ride更新時にapp/chair双方を無効化する。
cache生成中に状態が変わった場合も、保存前後のgeneration確認で古いresponseを残さない。さらに
`app_sent_at` / `chair_sent_at`がNULLだったresponseは保存しない。次pollで残りの未送信statusを
順番に取り出し、すべて送信済みになってから同一responseを再利用する。

matcherは通常の単発Hungarianではなく、128 ride × 64 chairのwindowを各pollで再計算するrolling方式を
維持した。ただし旧dummy waitの距離閾値`10 * speed`と5秒graceは狭すぎた。距離400未満は同windowで
即時割当、遠距離だけ見送り、300msを超えたrideはstarvation回避で割り当てるようにした。これは完全な
lifelong再割当てではないが、公式解説の「一定距離より遠い割当を見送る」とthroughputを両立する。

`4989df5`の合格runから最終runへの変化は次のとおり。

|---|---:|---:|---:|

| app notification total / avg / p95 | 18,323.7s / 36.9ms / 134.2ms | 3,690.1s / 3.1ms / 16.8ms | total -79.9% |
| chair notification total / avg / p95 | 7,284.8s / 38.3ms / 134.2ms | 3,808.9s / 11.0ms / 67.1ms | total -47.7% |

リクエスト数自体はthroughput増加で2倍以上になったが、notificationの累計時間とDB pool待ちは減った。
「回数を減らす」より「状態が変わらないpollをDBへ流さない」方が、この段階では正しかった。

### 9. coordinateの同期readを除去し、2地域matcherをpass/failで棄却した

`1d70444`の合格レポートでは`POST /api/chair/coordinate`が79,339回、累計2,851.0秒、
avg 35.9ms、p95 134.2msだった。椅子はcoordinate responseが返るまで次の移動を始めないため、
notificationより平均が30ms tickを超えるこちらを次のcritical pathと判断した。

`55ac627`では次の同期readを削除した。

- `chair_locations`へserver timestampをマイクロ秒精度で明示INSERTし、直後の同一row SELECTを廃止。
- latest ride statusをprocess内へcacheし、各status transactionのcommit後だけ更新。
- cacheは`MATCHING → ENROUTE → PICKUP → CARRYING → ARRIVED → COMPLETED`の単調増加だけを許可し、
  遅いcommitが新しい状態を巻き戻さない。
- resetでcacheを破棄し、miss時はDBを正として再構築。

通常test、race testに加え、変更関数は85.7〜100%のcoverageを確認した。ベンチは
**237,979 / pass**（`map[17:1 30:1]`）で、236,006から0.84%改善した。ただし中断後のsaveが
`StartedTTL=30m`を越え、`runctl: unknown run`でartifact化できなかった。完全なbench logは
`/root/isutools-bench-55ac627.log`へ残し、isutools側の契約不一致は
[#15](https://github.com/ekusiadadus/isutools/issues/15)へ分離した。

同じcommitの再走は[`20260806-130536.479964407-000001`](http://localhost:19191/20260806-130536.479964407-000001)
へ保存したが、189,013 / fail `32`だった。したがって「237,979が再現済みの安定score」とは主張せず、
最新の保存済み合格artifactは引き続き`1d70444`の236,006とする。

次に、軌跡で見えた2都市をmatcher windowで分離した。実DBでもride endpointは`-50..349`、
chair locationは`-81..367`で、境界150の地域判定が緯度・経度で食い違うrowは0件だった。
しかし結果は「地域分割すればよい」という単純なものではなかった。

| commit | artifact | score / gate | 判断 |
|---|---|---:|---|
| `2e75c85` | [`20260806-131258.633572787-000001`](http://localhost:19191/20260806-131258.633572787-000001) | **268,163 / fail `30,31,32`** | 地域ごとに128 ride / 64 chairを確保し越境禁止。最高scoreでも長時間未match 2件で不採用 |
| `7a1a1d3` | [`20260806-131650.119187922-000001`](http://localhost:19191/20260806-131650.119187922-000001) | 219,917 / fail `31,32` | 300ms超だけ余剰chairへglobal fallbackしたが長時間未match 1件が残存 |
| `15e2ddf`, `227a19c` | — | revert | 2実験を履歴ごと戻し、合格済みmatcherと同一コードへ復帰 |

地域ごとの公平な候補枠はthroughputを上げたが、全pending ride / free chairを`FOR UPDATE`で取得する
transaction延長と、地域ごとのchair供給偏りを同時に持ち込んだ。根本対応はDBの物理分割ではない。
次に試すなら、地域別read-only snapshotとcost計算をtransaction外で行い、短いcommit phaseで
`UPDATE ... WHERE chair_id IS NULL`を再検証する。region fairnessとlock保持時間を同じ変更へ混ぜず、
先にtransaction外計算だけを1ベンチで検証する。

`job_id / agent_id / assigned_at / released_at / reason`のappend-only履歴をアプリ側へ追加する。
詳細は[軌跡可視化ガイド](../TRAJECTORY_VISUALIZATION.md)を参照。

## Lifelong schedulerへ進む場合

次の段階はHungarianを別アルゴリズム名へ置き換えるだけではない。windowごとに次を状態として持つ。

1. 未割当rideに加え、まだcommit horizon外の仮assignment。
2. busy chairの予測完了時刻と予測完了位置。
3. pickup待ち、空走距離、ride価値、期限超過、assignment churnのcost。
4. 短い周期で再最適化しつつ、直近の実行だけをcommitするreceding horizon。
5. 旧planを破棄できるlease/generationとappend-only assignment history。

空間に障害物が導入された場合だけ、A*やtime-expanded path planningを下位の移動時間推定へ使う。
現在の格子Manhattan距離では、まず上位のdispatch schedulerと観測可能性を作る方が効果が大きい。

## ブログ本文で残す学び

1. **scoreよりpass/failを先に見る。** 高得点でも競合を偶然踏まなければ採用根拠にならない。
2. **1修正→1benchmark→保存を崩さない。** pool、stats cache、lock inversionの失敗を特定できた。
3. **短いSQLも回数で最大になる。** 1msでも40万回なら、indexよりpolling設計が先になる。
4. **pool waitは接続数増加の指示ではない。** 誰がslotを使うか、有用仕事が完了したかを見る。
5. **rolling Hungarianとlifelong最適化を区別する。** 再割当て履歴0件は、現在実装の限界を示す。
6. **可視化はalgorithmの説明責任になる。** scoreだけでなく、chairがどこからどこへ、いつ誰へ
   割り当てられたかを再生できると、次のcost設計を検証できる。
7. **失敗commitとartifactを消さない。** rollbackの理由こそ、後から最も価値のある判断ログになる。
8. **公式解説と実測を突き合わせる。** 一般論としてcacheするのではなく、30ms tickと約60万回の
   status selectが一致したためnotification response cacheを選べた。
9. **cache hitよりinvalidation contractが本体。** 未送信queueを1件目で塞ぐ実装は速くても失格する。
